# [Cross-Cutting] 多模态数据管理：AI 数据库的新前沿

> 多模态（图文音视频 + 结构化 + 半结构化）是 AI 系统数据管理的核心挑战之一。
> 当前的方案大多是"多个系统拼装"：向量库存 embedding、对象存储放原始文件、关系库管元数据。
> 统一多模态存储 + 事务一致性 + 混合检索还处于早期探索阶段。

---

## 一、问题定义：多模态 AI 系统面临的数据管理挑战

现代 AI 系统处理的数据类型已经远超传统文本：

| 模态       | 典型数据                 | 当前主流存储方案    | 存在的问题       |
| :--------- | :----------------------- | :------------------ | :--------------- |
| 文本       | 文档、对话记录           | 关系库 / 全文索引   | 相对成熟         |
| 向量       | Embedding                | 向量数据库          | 跟原始数据割裂   |
| 图像/视频  | 监控、医疗影像、工业质检 | 对象存储 (S3/MinIO) | 检索能力弱       |
| 音频       | 语音交互记录             | 文件系统            | 基本没有语义检索 |
| 结构化标签 | 标注、实体关系           | 关系库 / 图库       | 跟向量索引脱节   |
| 地理空间   | GPS 轨迹、地图           | PostGIS / 专用 GIS  | 跟其他模态不互通 |

一个典型的多模态 AI 应用（比如具身智能场景的机器人），需要同时管理视觉数据的 embedding、语音指令的转录文本、空间位置的 GIS 坐标、任务历史的结构化记录。当前实践中，这些数据散落在 3-5 个独立系统里，任何跨模态的查询都需要在应用层手动编排。

## 二、各层的多模态挑战

### L1 Storage：多模存储引擎

**核心问题**：一个存储引擎能不能同时高效管理向量、全文、JSON、关系、GIS 数据？

目前有三条技术路线：

1. **专用系统拼装**：Milvus (向量) + Elasticsearch (全文) + PostgreSQL (关系) + MinIO (对象)
   - 优势：每个组件在自己的领域都是最优
   - 代价：运维复杂、跨系统一致性靠应用层保证、JOIN 延迟高

2. **现有数据库扩展**：PostgreSQL + pgvector + pg_trgm + PostGIS
   - 优势：统一事务、统一查询接口
   - 代价：各模态的性能都不如专用系统（HNSW 规模上不去、全文检索不如 ES）

3. **原生多模数据库**：seekdb (OceanBase) 把向量/全文/JSON/GIS 在同一引擎内原生支持
   - 优势：混合查询在一条 SQL 内完成、ACID 一致性、部署简单
   - 代价：新系统生态不成熟、大规模场景的性能数据还不充分

seekdb 在这方面比较有参考价值——它的设计目标就是把上述多种数据类型合到一个 LSM-Tree 存储引擎里。一张表可以同时有 INT 列、VARCHAR 列、VECTOR 列、JSON 列，混合检索（向量召回 + BM25 + 标量过滤）在一个查询里完成。这省去了应用层拼接多个系统结果的麻烦，对事务一致性的保证也更直接。

**值得关注的研究方向**：
- 多模态 embedding 的统一管理（同一个实体的文本 embedding 和图像 embedding 是什么关系？要不要在存储层做对齐？）
- 跨模态联合索引（能不能建一个索引同时支持"按图搜图"和"按文搜图"？）
- 多模态数据的一致性语义（删掉一张图片时，其 embedding、描述文本、标注标签是否要原子删除？）

### L2 Memory：多模态记忆与 RAG

**核心问题**：Agent 的记忆不只有文本了，怎么管理视觉、听觉等多模态记忆？

当前的 Agent Memory 系统（MemGPT、Mem0、A-MEM）基本上只处理文本记忆。但在实际场景中：
- 具身智能的机器人需要记住"在 A 位置看到了什么物体"——这是**视觉 + 空间**记忆
- 智能客服需要记住"用户上次打电话说了什么"——这是**音频转文本 + 情感**记忆
- 自动驾驶需要持久化"某段路的历史视频帧和障碍物检测结果"——这是**视频 + 结构化标签**记忆

这些记忆在内存里是 multimodal embedding，持久化到数据库时面临的问题：
- 不同模态的 embedding 维度和距离度量可能不同
- 跨模态检索（用文字描述去搜视觉记忆）需要对齐的 embedding 空间（如 CLIP）
- 记忆蒸馏（从原始多模态数据提炼结构化知识）在多模态场景下更复杂

**多模态 RAG 的存储需求**：
传统 RAG（Lewis et al. 2020）只处理文本段落的检索。多模态 RAG 需要检索图片、表格、图表、公式等混合内容，对底层存储的要求包括：
- 同一个 chunk 可能同时包含文本向量和图片向量
- Reranking 需要考虑跨模态的相关性
- 索引需要支持混合查询：`WHERE type='image' AND vector_distance < 0.3 AND text LIKE '%手术%'`

seekdb 的 PowerRAG 管线在这方面有部分支持——文档入库时可以同时处理文本和表格（通过 AI_EMBED 自动向量化），查询时支持向量+全文+标量的混合检索。不过对于图片和视频等原始多媒体数据的处理，目前看还是依赖外部预处理。

### L3 Execution：多模态查询接口

**核心问题**：Text-to-SQL 之后，下一步是 Multimodal-to-Query？

当前的 DB Agent 基本都是文本输入 → SQL 输出。但真实场景在变化：
- 用户拍照问"这个零件的库存还有多少？" → 需要先做图像识别再查数据库
- 医生上传 CT 影像问"类似病例有哪些？" → 需要先做图像 embedding 再做相似度检索
- 工程师上传电路板照片问"这个故障见过几次？" → 需要多模态 RAG

这些场景的共同特点是：**查询入口从纯文本变成了多模态输入**。数据库执行引擎需要在查询规划阶段就处理多种模态的输入转换，这对传统 Text-to-SQL pipeline 是根本性的扩展。

seekdb 的 AI Functions（AI_EMBED、AI_COMPLETE）在一定程度上做了这件事——用户可以在 SQL 里直接调 LLM/Embedding 模型，不需要在应用层预处理。但完整的"多模态输入 → 查询规划 → 混合检索 → 结果融合"链条还没有谁做得很好。

## 三、云-边-端：多模态数据的部署挑战

这块直接跟 OceanBase/seekdb 的定位相关。具身智能场景的数据流大概是这样的：

```
端设备（机器人/车载/传感器）
  ↓ 本地采集多模态数据（视觉、音频、位姿）
  ↓ 本地数据库做实时查询和决策（低延迟要求）
  ↓ 定期同步到云端
云端数据库
  ↑ 做全量分析、模型训练、知识蒸馏
  ↑ 更新后的模型/知识下发回端侧
```

这个架构对端侧数据库的要求：
- **轻量**：机器人上不可能跑一个 Milvus 集群，需要 1C2G 就能用
- **多模**：视觉 embedding + 空间坐标 + 任务日志得在一个库里，否则端上维护多个系统不现实
- **一致性**：端云同步时要保证数据不错不漏
- **离线可用**：网络断了本地数据库还得正常工作

seekdb 的嵌入式模式（`pip install seekdb`，1C2G 运行）在端侧部署上有一定可行性。它支持向量、全文、JSON、GIS 的统一存储，跟云端 OceanBase 分布式版本 schema 兼容，理论上可以做端云数据同步。这个路线目前竞争对手不多——SQLite + FAISS 方案没有多模混合检索能力，pgvector 跑不了嵌入式。

## 值得注意的 gap

目前来看，多模态 AI 数据管理在数据库领域还没有被系统性地审视过。已有的综述（如 Zhao et al. 2023 的 LLM 数据管理综述、Zhou et al. 2024 的清华综述）都以文本为主，对图像、音频、视频的存储和检索基本没有展开讨论。

这是我们 survey 可以有差异化贡献的地方：把"多模态数据管理"作为一条纵向线索贯穿三层架构，而不是只在某一章提一下。
